# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Domain

This is a school management system for a **Bangladeshi school** that covers **Class 1 to Class 12** under the national curriculum (NCTB). Design new features for this context. Existing code doesn't enforce these rules yet, so don't assume it does.

- **Classes**: Class 1 to Class 12 only. Call them "Class" (Class 1 … Class 12), not "Grade", in the UI, seed data and copy.
- **Levels**: Primary (Class 1–5), Junior Secondary (Class 6–8), Secondary (Class 9–10, ending with the SSC exam) and Higher Secondary (Class 11–12, ending with the HSC exam).
- **Groups**: from Class 9, each student is in a group (Science, Business Studies or Humanities), and subjects can differ by group.
- **Grading**: the Bangladesh GPA scale: A+ 80–100 = 5.00, A 70–79 = 4.00, A- 60–69 = 3.50, B 50–59 = 3.00, C 40–49 = 2.00, D 33–39 = 1.00, F 0–32 = 0.00.
- **Academic year**: January to December.
- **Money**: Bangladeshi Taka (BDT, ৳), stored and sent as `decimal:2` per the API guideline.
- **Time**: store and send timestamps in UTC (the app's `APP_TIMEZONE`, which stays `UTC`). Asia/Dhaka is the school's local time, used for display and for date-only defaults such as today's attendance date.
- **Language**: names and content may be in Bangla or English, so don't assume ASCII (post and page slugs are the deliberate exception).

## Repository layout

The whole application is a **single Laravel 11 app in `backend/`**. It serves three surfaces:

- `/`: public school website, server-rendered Blade and built for SEO (`routes/web.php`, `app/Http/Controllers/Web`, `resources/views/public`)
- `/admin/*`: admin SPA in Vue 3 + Pinia + Vue Router, mounted by `resources/views/admin.blade.php` and bundled by Vite from `resources/js/admin`
- `/api/*`: JSON API (`routes/api.php`, `app/Http/Controllers/Api`)

There used to be a separate `frontend/` Vue app, but it has been removed and the admin SPA now lives entirely in `backend/resources/js/admin`.

## Commands

Run all of these from `backend/`:

```bash
composer install && npm install
cp .env.example .env && php artisan key:generate   # .env.example defaults to sqlite
php artisan migrate:fresh --seed                    # roles/permissions, admin user, sample public content
php artisan storage:link                            # public disk (post uploads) served from /storage

composer dev          # serve + queue:listen + pail logs + vite, all at once
npm run dev           # Vite only (HMR on :5173, strictPort)
npm run build         # production assets

php artisan test                                   # full suite (sqlite :memory:, see phpunit.xml)
php artisan test --filter=PublicSeoTest            # one class
php artisan test --filter=test_public_page_is_server_rendered_with_seo_tags
./vendor/bin/pint                                  # code style (Laravel Pint)
```

Docker alternative (run from the repo root): `docker compose up` starts MySQL (host port 3307, db `scms`), the app on :8000 and Vite on :5173.

Seeded admin login: `admin@sms.com` / `password`.

## Architecture notes

- **Auth**: the admin SPA uses Sanctum **bearer tokens** stored in `localStorage` (`resources/js/admin/services/api.js`), not cookie/session auth. A 401 response clears the token and redirects to `/admin/login`. The Vue router uses `createWebHistory('/admin/')`, and the catch-all `Route::view('/admin/{any?}', 'admin')` in `web.php` serves every admin path.
- **Roles and permissions**: Spatie Permission. The `role` and `permission` middleware aliases are registered in `bootstrap/app.php`. Roles (admin/teacher/student/parent) and kebab-case permissions like `view-students` come from `RolePermissionSeeder`. Every authenticated API controller declares per-action permissions through `HasMiddleware` and `Controller::resourcePermissions()`, except posts and pages, which use `role:admin`. `tests/Feature/ApiAuthorizationTest.php` fails if a route lacks a check, so new routes need a mapping or an explicit entry in its allowlist. Sections reuse the `*-classes` permissions, exam schedules reuse `*-exams`, and academic years are readable by any user but need `edit-settings` to change. Permissions are role-wide: nothing limits teachers to their own students, and parents and students don't have `view-students` at all (they use `/api/my/children` and `/api/my/student`, see the Students note).
- **Shared public content**: news and events are a single `Post` model split by `type` (`Post::TYPE_NEWS` / `TYPE_EVENT`). `App\Services\PostService` holds the read queries. Both the Blade site (`Web\PostController`) and the unauthenticated mobile-app API (`Api\PublicContentController`, `/api/public/*`, output through `PostResource`) use it, so the two always return the same data. Put new public-content queries in the service, not in a controller. Contact form submissions work the same way: `ContactService` (its validation rules are `ContactService::RULES`) is shared by the web form and `/api/public/contact`.
- **Post model behavior**: slugs are generated automatically and kept unique. Setting `is_published` fills in `published_at`. The `published()` scope also requires `published_at <= now()`. Saving or deleting a post clears the cached `sitemap.xml` (cached for 1 hour in `SeoController`). Post bodies are sanitized HTML, written by the Tiptap editor in the admin SPA and stored as-is: `App\Services\PostService::create()`/`update()` sanitize with `App\Support\PostBody::sanitize()` (the `post_body` profile in `config/purifier.php`, via `mews/purifier`) and reject a body that is empty after sanitizing. `PostBody::plainText()` produces the excerpt and meta-description fallbacks. The public page renders the stored HTML directly (`{!! $post->body !!}` in `resources/views/public/posts/show.blade.php`); there is a single render path, so nothing re-sanitizes on read. Uploaded images go through `POST /api/posts/media` (admin only) to the `public` disk under `posts/{Y}/{m}/{uuid}.{ext}`, served from `/storage/...` (`php artisan storage:link`). A one-off data migration converted bodies written before this feature (Markdown, rendered with `Str::markdown` at read time) to sanitized HTML.
- **Pages module**: standalone public content pages (policies, facilities, etc.), a full module on the Controller → Service → Repository pattern (`App\Models\Page`, `PageRepositoryInterface`/`PageRepository`, `PageService`, `Api\PageController` at `/api/pages`, `role:admin` like posts). Slug generation, the `published()` scope, sitemap-cache clearing on save/delete, and `PostBody::sanitize()`/`isEmpty()` on the body all mirror `Post`, reusing the same `post_body` purifier profile and `POST /api/posts/media` upload endpoint from the admin editor. The public route is `GET /pages/{slug}` (`Web\PageController`, view `resources/views/public/pages/show.blade.php`), named `page.show` (singular) so it doesn't collide with the `pages.show` name Laravel generates for `apiResource('pages', ...)`. Admins manage pages, and separately News and Events (same `Post` model, different `type`), under the sidebar's collapsible **CMS** group (`resources/js/admin/views/Layout.vue`); `/news` and `/events` reuse `PostList.vue`/`PostForm.vue` with the type fixed by route `meta.type`, and the old `/posts` routes redirect to `/news`. About and Admissions stay hardcoded Blade, not Page records.
- **Menu module**: the public header nav is an admin-managed, nested tree (`App\Models\MenuItem`, `MenuItemRepositoryInterface`/`MenuItemRepository`, `MenuService`, `Api\MenuItemController` at `/api/menu-items` plus `PUT /api/menu-items/reorder`, `role:admin` like pages). Each item has a `location` (only `header` for now), a self `parent_id` (`cascadeOnDelete`, so deleting a parent deletes its children), a `type` of `page`/`route`/`url`/`heading`, and the matching target field; `route_name` is whitelisted to `MenuItem::ROUTES`. `MenuService` enforces a maximum depth of 3, no cycles, the parent staying in the same location, and the target required by `type`, all as `ValidationException`s. `MenuService::headerTree()` builds the nested, filtered tree (dropping unpublished/missing-page items and headings left with no visible children) and caches it forever under `menu.header`; `MenuItem` and `Page` save/delete hooks both forget that key, so publishing state changes take effect on the next request. `App\View\Composers\HeaderMenuComposer` shares it with `layouts/public.blade.php` as `$headerMenu`, rendered by the `<x-header-menu>` component (`resources/views/components/header-menu.blade.php`): CSS-only dropdowns on desktop (Tailwind named groups `group/lvl1`/`group/lvl2`, no JS) up to 3 levels, a `<details>` hamburger on mobile, and a hardcoded six-link fallback when the tree is empty. Admins manage it at `/admin/menu` (`views/menu/MenuList.vue`, `MenuForm.vue`), grouped under the sidebar's **CMS** section.
- **Media and Gallery modules**: photo/video galleries on the public site, two full modules on the Controller → Service → Repository pattern, `role:admin` like pages and menu. `App\Models\Media` (table `media`) is the reusable image library: one row per upload (`disk`/`path`/`original_name`/`mime_type`/`size`/`width`/`height`/nullable `alt`), managed at `/api/media` (`Api\MediaController`, index/store/update/destroy only — no `show`) and browsed/edited/deleted at `/admin/media` (`views/media/MediaLibrary.vue`). `App\Models\Gallery` (slug generation, `published()` scope and sitemap-cache clearing all mirror `Page`) holds ordered `App\Models\GalleryItem`s of `type` `image` (a `media_id`, restricted on delete so a library image in use can't be removed) or `video` (a `youtube_url` plus the `youtube_id` extracted from it); items are never a separate endpoint; the gallery's own store/update payload carries an `items` array that `GalleryService::syncItems()` (via `GalleryRepository`) creates/updates/deletes/reorders in one transaction, position in the array becoming `sort_order`. `items.*.media_id`/`items.*.youtube_url` are `prohibited_unless` the matching `items.*.type`, on top of the existing `required_if`, so an image item can't also carry a `youtube_url` or vice versa. `GalleryResource::withItems()` mirrors `PostResource::withBody()`: lists (`index`, `/api/public/galleries`, the `/gallery` and `/admin/galleries` grids) never carry every gallery's full `items` array, only `cover_url` and `item_count`, computed from a narrower eager load (`Gallery::firstImageItem()`/`firstVideoItem()`, one-of-many relations) instead of `items.media`; only `show`/`store`/`update` and `galleriesShow` opt in with `withItems()`. `App\Support\YouTube` is the one place that recognizes a YouTube URL (`watch?v=`, `youtu.be/`, `embed/`, `shorts/`, `m.youtube.com`) and extracts the 11-character id, used by both `Http\Requests\Gallery\Rules\ValidYoutubeUrl` (422 on anything else, including lookalike hosts) and `GalleryService`; the public page embeds `youtube-nocookie.com/embed/{id}` and uses `i.ytimg.com/vi/{id}/hqdefault.jpg` as the thumbnail. A gallery's cover is `cover_media_id` if set (`nullOnDelete`, so deleting that image falls back automatically), otherwise the first image item, otherwise the first video's thumbnail, otherwise null (the view/resource shows a placeholder). `Api\GalleryController` exposes the admin CRUD at `/api/galleries`; `Web\GalleryController` serves `GET /gallery` (`gallery.index`, paginated, 404 out of range) and `GET /gallery/{slug}` (`gallery.show`, a CSS-only `:target` lightbox for photos — see `.gallery-lightbox` in `resources/css/public.css` — and responsive video embeds), both through `GalleryService` so they and `Api\PublicContentController::galleries()`/`galleriesShow()` (`/api/public/galleries`) always agree; `gallery.index` is in `MenuItem::ROUTES`. Admins manage galleries at `/admin/galleries` (`views/galleries/GalleryList.vue`, `GalleryForm.vue`), adding items through the reusable `components/MediaPickerModal.vue` (a Library tab to search and multi-select existing images, an Upload tab that uploads new ones and selects them), under the sidebar's **CMS** group. `Database\Seeders\GallerySeeder` (called from `DatabaseSeeder`, matched by slug so re-running it never duplicates) draws placeholder JPEGs with GD straight to the `public` disk (no network) for a handful of Bangladeshi-school galleries.
- **Institute settings**: the school's identity, branding, contact details and address are admin-managed, not hardcoded. A generic `settings` table (`App\Models\Setting`: `key` unique, `value` text) backs it; `App\Support\InstituteSettings` is the registry of every key the "institute" group uses (grouped as identity/branding/contact/address/location/social, plus the education board and division option lists and the validation rules for each key). `App\Services\InstituteSettingsService::all()` returns every registry key (null when unset), cached forever under `settings.institute`; `update()` upserts only the keys that were sent, stores `logo`/`favicon` uploads as `settings/{uuid}.{ext}` on the `public` disk, deletes the old or removed file only after the write commits, and forgets the cache. `profile()` is the effective public read: it falls back field-by-field to `config('seo.*')` so an empty table renders exactly as it did before this module existed, and it's the only thing public readers use — never `all()` or `config('seo.*')` directly. `Api\InstituteSettingsController` exposes `GET`/`PUT /api/settings/institute` (`view-settings`/`edit-settings`, the same permissions `AcademicYearController` uses for its own settings actions); the admin SPA page is `views/settings/InstituteSettings.vue`, first in the sidebar's **CMS** group. `App\View\Composers\InstituteComposer` shares `profile()` as `$institute` with `layouts.public`, every `public.*` view, `components.seo` and `admin`, so the header logo/name, footer address, the contact page, `<title>`/favicon and `App\Support\SchemaOrg`'s JSON-LD (`alternateName` from `name_bn`, `geo` when both coordinates are set, and `addressCountry` hardcoded to `BD`) all read from the same values. `Api\PublicContentController::school()` (`/api/public/school`) reads the same `profile()` and keeps every pre-existing key alongside the new ones.
- **SEO**: every public page yields a `<x-seo>` component (`resources/views/components/seo.blade.php`) into the `seo` section of `layouts/public.blade.php`. The component handles the title, description, canonical URL (via `App\Support\Seo::canonical()`, which keeps only `?page=N` when N > 1), OG/Twitter tags and JSON-LD (built with `App\Support\SchemaOrg`). Site and organization values come from `App\Services\InstituteSettingsService::profile()` (the admin-managed institute settings), falling back field-by-field to `config/seo.php` (`SEO_*` / `SCHOOL_*` env vars) when a setting is unset. `tests/Feature/PublicSeoTest.php` requires each public page to have the full SEO head and **exactly one `<h1>`**, and requires unknown or draft posts/pages to return a noindex 404. `Web\PostController` also returns 404 for out-of-range pagination pages. Keep new public pages consistent with these rules.
- **Vite entries**: there are two, `resources/css/public.css` (the public site, Tailwind) and `resources/js/admin/main.js` (the admin). The `@` alias points to `resources/js/admin`.
- **Model naming quirks**: the class model is `App\Models\Classes` (table `classes`), because `Class` is a reserved word. The class–section pivot is `ClassSection`. A guardian is a `User` with the `parent` role (`User::children()` returns their students); there is no parent model.
- **Stub controllers**: these API controllers are empty 12-line stubs even though `api.php` registers routes for them: FeeType, FeeStructure, FeePayment and Dashboard. For now, `index` returns `{"data": []}` and the other actions return 501. The extra routes (`dashboard/stats`, `dashboard/recent-activities`, `fee-payments/student/...`, `fee-payments/receipt/...`) point at methods that don't exist yet, so they return 500. The admin views that use them are mostly placeholders too.
- **Staff and Shifts modules**: current and former teaching/non-teaching staff, shown on the public স্কুল প্রশাসন (School Administration) pages, and the shifts they belong to. Both are full modules on the Controller → Service → Repository pattern, replacing the old placeholder `Teacher` model/table/`TeacherController` stub wholesale (`subject_assignments.teacher_id` is repointed to `staff_id`, and `SubjectAssignment::staff()` replaces `::teacher()`). `App\Models\Staff` (table `staff`, soft deletes) has a nullable `user_id` (logins are linked later), `category` (teacher/staff), `position` (head/assistant_head/teacher/staff), `status` (active/retired/transferred/resigned/deceased), and the usual personal/contact/address fields; `name_en`/`name_bn` each may be blank but not both (enforced in `StaffService`, not the database, so it's still checked on a partial update against the model with the input applied — the same pattern as `SubjectService::ensurePassMarksWithinTotal()`). `App\Models\StaffEducation`/`StaffTraining` (tables `staff_educations`/`staff_trainings`) are child rows managed entirely through the staff store/update payload's `educations[]`/`trainings[]` arrays, synced like `GalleryService::syncItems()` (`StaffRepository::syncEducations()`/`syncTrainings()`; each re-fetches `$staff->{$relation}()` fresh for every query rather than reusing one builder, because `HasMany` forwards `where()`/`whereKey()` onto the same underlying query instance, so reusing it would let one iteration's `whereKey()` narrow every later call including the final delete). `App\Models\Shift` (table `shifts`) holds `name_en`/`name_bn`, a unique ASCII `slug`, and nullable Asia/Dhaka wall-clock `start_time`/`end_time`; every staff member has at least one shift via the `shift_staff` pivot. `StaffService` enforces: a non-`active` status requires `leaving_date`; `leaving_date` must be on/after `joining_date`; and each shift can have at most one active `head` and one active `assistant_head` (`StaffRepository::hasActiveInPosition()`). Photo replace/remove follows `InstituteSettingsService::update()`'s file-handling pattern (delete the new file on failure, the old one after commit). `Api\StaffController` (`/api/staff`) reuses the `*-teachers` permissions from `RolePermissionSeeder`; `Api\ShiftController` (`/api/shifts`) reuses `view-settings`/`edit-settings` like `AcademicYearController` (reads open to any signed-in user, writes need `edit-settings`). `Web\StaffController` serves the 7 public index pages (`staff.head`/`assistant_head`/`teachers`/`employees`/`ex_heads`/`ex_teachers`/`ex_employees` at `/administration/...`) and `staff.show` (`/administration/staff/{staff}`), all through `StaffService::publicList()`/`publicFind()`, the same methods `Api\PublicContentController::staff()`/`staffShow()` (`/api/public/staff`) use, so the website and the mobile API always agree; neither ever exposes `nid`, `date_of_birth`, addresses or `mpo_index`, and `mobile`/`email` only appear when `show_contact` is set (`StaffResource::public()`, mirroring `GalleryResource::withItems()`). List pages take an optional `?shift={slug}` filter, resolved by `StaffService::resolveActiveShift()` (aborts 404 for an unknown or inactive slug, matching an unknown page/post slug); the filter pills only render when more than one active shift exists. The head/assistant-head pages render each matching person's full profile inline rather than a card grid, since a school can have a different head per shift. All 7 index routes are in `MenuItem::ROUTES`, the `MenuForm.vue` route options, and the sitemap (profiles too); `MenuSeeder` adds a স্কুল প্রশাসন heading with the 7 as children. `Database\Seeders\ShiftSeeder` creates the two real shifts (Morning/Day); `Database\Seeders\StaffSeeder` reads a committed fixture (`database/seeders/data/staff.json`, photos in `.../staff-photos/`) captured by a one-off, out-of-tree scrape of vhbub.edu.bd.shongket.com and never touches the network itself, matching existing rows on `employee_id = VHBUB-{source_id}` so reruns update instead of duplicating, and writes through the models directly (bypassing `StaffService`'s validation rules, since the source data doesn't always show a leaving date for former staff). Admins manage staff at `/admin/staff` (`views/staff/StaffList.vue`, `StaffForm.vue`; the old `/admin/teachers` link redirects there) and shifts at `/admin/shifts` (`views/shifts/ShiftList.vue`, `ShiftForm.vue`).
- **Academic structure**: Classes, Sections and Academic Years, converted wholesale to the Controller → Service → Repository pattern (Subjects/Staff/Shifts are the reference). `App\Models\Classes` (table `classes`, soft deletes; named `Classes` because `Class` is reserved) adds `number` (unique, 1-12) and nullable `name_bn`; the level (`primary` 1-5, `junior_secondary` 6-8, `secondary` 9-10, `higher_secondary` 11-12) and `has_groups` (`number >= 9`) are derived from `number` by `Classes::level()`/`hasGroups()`, never stored. `App\Support\AcademicGroup` holds the three groups (science/business_studies/humanities) with English/Bangla labels; it's stateless, not a table. `App\Models\Section` adds a required `shift_id` (FK `restrictOnDelete`) and a nullable `group`, allowed only when the class's number is 9 or above — checked in `SectionService` against the model with the input applied, the same pattern as `StaffService::ensureCategoryMatchesPosition()`. The unique key is `(class_id, shift_id, code)`; `class_id` can't change once a section exists (`UpdateSectionRequest`'s `prohibited` rule). `App\Models\AcademicYear` adds a unique `year` (2000-2100); `start_date`/`end_date` default to Jan 1/Dec 31 of `year` and must stay inside that calendar year (`AcademicYearService`, checked on partial updates too), and `code` defaults to the year. `AcademicYearService::activate()` runs in a transaction and deactivates every other year, so exactly one stays active. `App\Models\ClassSection` (table `class_sections`) is a section's class teacher (staff) per academic year, replacing its old `class_teacher_id` (users) column; unique on `(section_id, academic_year_id)` and `(academic_year_id, staff_id)`, so a teacher leads at most one section per year (the endpoints return a narrow staff shape — id, names, designation, photo_url — never the admin `StaffResource`, since the `teacher` role has `view-classes` but not `view-teachers`; changing a section's `shift_id` is rejected while a class teacher isn't in the new shift, and lowering a class's `number` below 9 is rejected while any of its sections has a group) (`App\Services\ClassTeacherService`, also enforced against the staff member being active, `category=teacher`, and belonging to the section's shift). It has no standalone CRUD endpoint: `GET /api/sections/{section}/class-teachers` (one row per year) and `PUT /api/sections/{section}/class-teacher` (`{academic_year_id, staff_id|null}`, `null` unassigns and removes the row; `permission:view-classes`/`edit-classes`) live on `Api\SectionController`, backed by `App\Repositories\Eloquent\ClassTeacherRepository` (a narrower contract than the base `RepositoryInterface`, since there's nothing to paginate). Every delete guard checks references soft deletes don't protect (mirroring `SubjectService::delete()`): classes block on sections/students/attendances/exam schedules/fee structures/subject assignments; sections block on students/attendances/exam schedules/subject assignments (their class-teacher rows don't block — they're deleted in the same transaction); academic years block while active or referenced by students/exams/fee structures/class-teacher rows/subject assignments; `ShiftService::delete()` and `StaffService::delete()` gained a section-usage and class-teacher guard respectively. `academic-years` keeps its existing permission split (any signed-in user reads, `edit-settings` writes); `classes`/`sections` keep the `*-classes` permissions. `Database\Seeders\ClassSeeder`/`AcademicYearSeeder`/`SectionSeeder` (idempotent, matched on `number`/`year`/`(class_id, shift_id, code)`) seed Class 1-12, the 2026 active year, and a Section A per class per shift. Admins manage all three at `/admin/classes`, `/admin/sections` and `/admin/academic-years`, grouped under the sidebar's collapsible **Academic** section; `SectionList.vue` assigns/unassigns class teachers inline for a chosen academic year (defaulting to the active one), loading eligible teachers from `/api/staff?category=teacher&is_active=1&shift={id}`.
- **Students and Auth**: students, their guardians' logins and yearly enrolment, plus the sign-in module, all on the Controller → Service → Repository pattern (the legacy `StudentController` and `AuthController` were converted wholesale, and the never-used `parents`/`parent_student` tables, `ParentModel`, `ParentController`, `/api/parents` and the `*-parents` permissions were removed; the migration `2026_10_02_000001` deletes the old Indian-style student rows, every user with the `student` or `parent` role, and the attendance/exam-result/fee-payment rows that pointed at students, and `down()` restores only the old table structure). `users` gained a nullable unique `username` and `email` became nullable: a student's login username is their `student_id`, a guardian's is their mobile number (`01XXXXXXXXX`, `App\Support\Mobile::normalize()` strips `+88`). `App\Models\Student` (table `students`, soft deletes) has a Bangladeshi profile (`name_en`/`name_bn` with at least one required, checked in `StudentService` like Staff; `gender`, `religion`, `blood_group`, unique 17-digit `birth_registration_number`, `nationality`, `mobile`, `email`, addresses, `district`, `photo`), `admission_date`, `status` (active/left/graduated) with `leaving_date` (required when not active, not before admission), the father's and mother's details, and the guardian block (`guardian_relation`, `guardian_name`, `guardian_mobile`, `guardian_user_id`); `user_id` is the student's own login. `student_id` is generated as `{admission year}{sequence of at least 4 digits}` (`StudentRepository::nextStudentId()`, which keeps growing past 9999 instead of wrapping; a concurrent clash surfaces as a 422 on `student_id`). `App\Models\StudentEnrolment` (table `student_enrolments`) is one row per student per academic year (unique on `(student_id, academic_year_id)`): `section_id` (the `class_id` is always the section's), `group`, `optional_subject_id` (the 4th subject), `roll_number` (unique per section per year, also a DB unique index, NULLs allowed) and `status` (active/promoted/retained/left/graduated); a student's class, group and roll therefore live only there, and `Classes`/`Section`/`AcademicYear::enrolments()` replaced their old `students()` relations (the existing `hasStudents()` delete guards now check enrolments; `SubjectService::delete()` returns 409 while an enrolment uses the subject as its 4th subject). `App\Services\EnrolmentService` enforces, inside the caller's transaction and with errors keyed `enrolment.{field}`: the section must be active and on an active shift and have a free seat (checked only when the enrolment starts taking a seat: a new active enrolment, a move into another section, or one turning active again; editing a student who keeps their seat, or saving a student who is not active, is never blocked), a group is required from Class 9 and forbidden below it and must match the section's group, the 4th subject is forbidden below Class 9 and must be an `optional` curriculum row for the class and group (reusing `ClassSubjectRepositoryInterface::forClassAndGroup()`), and the roll number is free in that section and year. The section row is locked first (`StudentEnrolmentRepository::lockSection()`, returning the fresh row with its class and shift) so concurrent enrolments queue up on capacity. An enrolment's status follows the student's (left/graduated free the seat; promoted/retained rows are history and untouched). `App\Services\StudentService` creates the student, the student login (role `student`, password from the admin), the enrolment for the **active academic year** (422 on `enrolment.section_id` when none is active) and the guardian login in one transaction: the guardian login is the `parent` user whose `username` equals `guardian_mobile`, shared by siblings; a new one, or an existing but deactivated one (the number may have been recycled to someone else), needs `guardian_password` (422 on `guardian_password` otherwise; the new password is set and the old tokens revoked before it is reactivated), and the login's name follows the latest `guardian_name` written and a mobile owned by a non-parent user is a 422 on `guardian_mobile`. Changing `guardian_mobile` relinks the student, and a guardian login is active only while at least one non-deleted student of it has status `active` (`syncGuardianAccess()`, also run on status change and delete); the student login's `is_active` follows the student's status, and deactivating a login revokes its tokens. `password`/`guardian_password` are optional on update and reset the matching login. Delete returns 409 while the student has attendance, exam results or fee payments, otherwise soft-deletes; the active-year enrolment is kept as history but marked `left` with its roll number cleared (`EnrolmentService::release()`), so the seat and roll are free again, and `countActiveInSection()`/`rollNumberTaken()` also ignore soft-deleted students. Auth: `Api\AuthController` is thin over `App\Services\AuthService` and `UserRepositoryInterface` (`findForLogin()` matches the identifier, lowercased for email since emails are stored lowercased by the student requests, against email, `username` and the normalized mobile). `POST /api/login` takes `login` (an email, student ID or mobile; `email` still works as an alias), `password`, optional `device_name`, and returns `{data: {token, user}}`; `GET /api/me` returns `{data: user}`; `logout` and `change-password` return `{message}`; a wrong password or an inactive account is a 422 on `login`; `POST /api/login` is throttled in two places, and every 429 is `{message}` with a `Retry-After` header: the named `login` rate limiter (registered in `AppServiceProvider`) allows 5 attempts a minute per normalized login identifier plus IP, and `AuthService::login()` (which receives `$request->ip()` as a string) counts failed passwords only, never successes: 30 a minute per IP under `login-ip-fail:{sha1(ip)}` (once tripped it refuses everyone on that IP, even with the right password, so a school behind one IP isn't throttled by its own sign-ins), and 10 a minute per resolved user id under `login-user:{id}` (any IP or spelling, cleared on success, because MySQL's collation can resolve accent or script variants of an identifier to one user). A successful login marks that user and IP pair as trusted for 30 days (`login-trusted:{id}:{sha1(ip)}` in the cache), and a trusted IP skips the per-account lock, so an attacker hammering a known account from elsewhere can't keep its owner out; the per-IP limit still applies to it, and `change-password` revokes the user's other tokens. These limits key on `$request->ip()`, which assumes the app is not behind a proxy: no `trustProxies` is configured in `bootstrap/app.php` yet, and behind Cloudflare or a load balancer every visitor would share the proxy's IP (one 30-failure burst would block the whole site and one trusted IP would cover everyone), so configure `trustProxies` when hosting is chosen. Accepted trade-offs: a user with no trusted IP yet (first login or a new device) can still be locked out for a minute at a time, and someone on a shared school network can block that network for a minute with 30 bad attempts. - **Exam results and GPA**: processing an exam's marks into results, publishing them, and reading them back, on the Controller → Service → Repository pattern. `App\Support\Gpa` is the stateless helper with every grading rule (like `Seo`, no database): `gradeFor()` (the CLAUDE.md scale on a percentage compared half-up on 2 decimals), `unit()` (grades one subject, or a pair of papers combined), `result()` (GPA, overall grade, pass, failed count, totals), `gradeForGpa()` and `positions()`; all arithmetic is on integer hundredths so rounding is exact, and every number is sent as a `decimal:2` string. A **unit** is one subject, or the papers sharing a `paper_group` among the subjects the student takes (a group with one row is a single subject); it fails (F, 0.00) when the student was absent from any paper or any part's marks, summed across the papers, are below that part's pass marks summed across the papers; otherwise the grade comes from combined obtained over combined full. The student's **compulsory units** are every `compulsory` row they take (common rows plus their group's); the **4th subject** is the optional row matching the enrolment's `optional_subject_id`. GPA = (compulsory points + max(0, 4th-subject point - 2)) / number of compulsory units, capped at 5.00 and rounded half-up; any compulsory F makes the GPA 0.00, the grade F and the student failed, while failing the 4th subject never does. The overall grade is A+ at 5.00, then A from 4.00, A- from 3.50, B from 3.00, C from 2.00, D from 1.00, else F. `total_obtained`/`total_full` include the 4th subject. Merit positions use standard competition ranking (1, 2, 2, 4) within the class and, separately, within the section: passed first, then GPA, then total (roll number only orders the display). `App\Models\ExamResult` (`exam_results`, one row per `(exam_id, enrolment_id)`) stores the totals, `gpa` (`decimal:2`), `grade`, `is_pass`, `failed_count`, `class_position`, `section_position` and a `subjects` JSON with one entry per unit (`exam_subject_ids`, `subject_ids`, `name_en`/`name_bn` (a pair's names joined with ` + `), `is_optional`, `is_combined`, per-`papers` detail, combined `parts` (`obtained`/`full`/`pass`), `obtained`, `full`, `percentage`, `grade`, `point`, `is_absent`), so a published result keeps the grading it was given. `ResultService` (`ExamResultRepository`, a narrow contract; the "who takes which subject" rule lives once in `StudentEnrolment::scopeTakingSubject()`/`scopeActiveIn()` and is shared with the mark sheets) does `process()`: under the exam lock, from `marks_entry` or `processed` (409 for a draft or published exam), it recomputes every active enrolment of the exam's year in every class of the exam (not soft-deleted students), replaces the exam's results in one transaction and sets `processed`; a paper with no mark row, or a non-absent mark row missing one of the paper's parts, counts as absent (an F) and is reported as `missing_marks` in the per class-and-section summary (`students`, `passed`, `failed`, `missing_marks`) the process response carries next to the exam. `publish()` needs `processed` (409 otherwise) and sets `published_at`; `unpublish()` returns to `processed`. Saving marks into a `processed` exam sets it back to `marks_entry` (see Exams and marks), so stale results can't be published; a published exam still rejects marks (409). Known limit: a change that isn't a mark (an enrolment moved or removed, a class dropped from an unmarked exam) doesn't reset a `processed` exam, so process again before publishing. `Api\ExamResultController` has `POST /api/exams/{exam}/process|publish|unpublish` (`publish-exams`, teachers don't have it) and `GET /api/exams/{exam}/results?class_id=&section_id=&with_subjects=` (`view-results`; paginated tabulation ordered by section position when a section is filtered, otherwise class then class position; `ExamResultResource` rows carry a narrow student, roll, group, class and section, and `subjects` only with `with_subjects=1`, like `PostResource::withBody()`) and `GET /api/exams/{exam}/results/{student}` (the full breakdown, 404 without a result); the student and parent roles have no `view-results`. Own records, through `MyRecordsController` and `ResultService` (published exams only, so an unpublished or unpublished-again exam disappears): `GET /api/my/results` (`role:student`, the student's results with the full breakdown, 404 when no student record is linked), `GET /api/my/children/{student}/results` (`role:parent`; `StudentService::findChildOf()` gives 403 for any student who isn't the guardian's own, existing or not) and `GET /api/my/exams` (student or parent: one entry per student with the exams of their class in the active year that are not drafts, each listing only the subjects the student takes, with subject, date and time and no marks scheme). Report cards are a print-friendly SPA page, no PDF library: `views/exams/ReportCards.vue` at `/admin/exams/:id/report-cards?class_id=&section_id=` (and `/report-cards/:studentId` for one student) loads the results with `with_subjects=1`, the exam and `/api/public/school`, and prints one card per page (`@media print`, `break-after: page`, the sidebar and top bar hidden through a `report-cards-page` class on `<body>` while the page is mounted) with Noto Sans Bengali from Google Fonts; `views/exams/ExamResults.vue` at `/admin/exams/:id/results` has the Process, Publish and Unpublish buttons, the processing summary and the tabulation, linked from `ExamList.vue`. `ExamSeeder`'s HY-2026 exam can be processed straight away. Known curriculum limit: the curriculum can't express "Biology or Higher Math, one compulsory and the other the 4th subject", because the 4th subject is fixed per group (an `optional` row), so choosing which Science subject is the compulsory one per student is not supported; weighted or combined results across exams and promotion from results are also out of scope.

## Development workflow

This repo ships a per-task agent harness under `.claude/`: slash commands, two subagents,
a smoke script and a `PreToolUse` gate hook. A task flows **spec → task file → branch →
code → test → smoke → commit → review → PR**.

**Who does what.** The main session (usually Opus) plans, asks the user questions,
delegates and reports. It does **not** write product code itself. Code comes from Sonnet:
the **`implementer`** subagent writes features, fixes and review follow-ups, and
**`test-runner`** fixes failing tests. Review comes from **`code-reviewer`** on Opus, so
the code is always reviewed by a different model from the one that wrote it.

- **`/new-task <spec>`** grooms the spec (problem, scope, acceptance criteria and
  **explicit test cases**), saves it to `docs/tasks/<slug>.md` (template in
  `docs/tasks/README.md`), and cuts `feat/<slug>` or `fix/<slug>` from `main`.
- **`/implement <task file | description>`** hands the task to `implementer` (Sonnet),
  checks the diff stays in scope, and reports. Follow-up fixes go back to `implementer`.
- **`/new-module <Model>`** plans a backend module and has `implementer` build it to the
  architecture guideline, using Subjects as the reference: repository interface and implementation, binding,
  service, FormRequests, resource, controller with permissions, routes and tests.
- **`/wrap-up [base]`** runs the end-of-task gate in this order:
  1. The **`test-runner`** subagent runs `php artisan test`, Pint on files added on this
     branch, and the hook classifier tests. It fixes failures until green.
  2. **Smoke:** `bash .claude/scripts/smoke.sh` seeds a throwaway SQLite database, boots
     the app on :8123, checks the public pages, `/admin`, the public API, an
     unauthenticated 401 and an admin login, then tears everything down. It never
     touches your real database.
  3. It updates the task file, then **asks** before committing.
  4. The **`code-reviewer`** subagent (read-only, runs on Opus, a different model from
     the Sonnet writer) reviews `base...HEAD` against `CLAUDE.md` and both guidelines, then
     records its verdict.
  5. If everything is green, it **asks** whether to push and open the PR.
- **`/pr-review [base]`** runs only the review step, for example after a fixup commit.
  It refuses on a dirty tree.
- Both review commands stop after **2 consecutive `changes-requested`** verdicts and hand
  the decision back to the user.

**Automated gates** (`.claude/hooks/gate.sh`, with commands classified by `classify.py`):
- `git commit` is denied on `main` or `master`. Use a task branch.
- `gh pr create` is denied unless `code-reviewer` recorded `pass` or `pass-with-nits` for
  the **exact current HEAD** on a clean tree. Receipts live in `.claude/.review-gate/`
  (gitignored, per machine).
- **`.claude/.review-gate/OVERRIDE`** disables both gates. Only the user creates it, by
  hand, outside Claude Code. Any tool call that tries to create or edit it is denied, and
  an agent must never suggest working around the gate by creating it.
- The hook is a cooperative guard, not a security boundary. Before changing
  `classify.py` or `gate.sh`, read their headers, then run
  `python3 .claude/hooks/test_classify.py`. Every case in it is a real bypass that was
  found and fixed.

## Architecture layers

Backend features follow Controller → Service → Repository interface → Eloquent repository. Controllers only handle HTTP, services hold the business rules and transactions, and repositories are the only place that builds queries. Every interface is bound in `RepositoryServiceProvider`. Subjects is the reference module. Legacy modules are converted only when they're otherwise being changed.

@docs/architecture-guidelines.md
