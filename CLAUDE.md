# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Domain

This is a school management system for a **Bangladeshi school** that covers **Class 1 to Class 12** under the national curriculum (NCTB). Design new features for this context. Existing code doesn't enforce these rules yet, so don't assume it does.

- **Classes**: Class 1 to Class 12 only. Call them "Class" (Class 1 … Class 12), not "Grade", in the UI, seed data and copy.
- **Levels**: Primary (Class 1–5), Junior Secondary (Class 6–8), Secondary (Class 9–10, ending with the SSC exam) and Higher Secondary (Class 11–12, ending with the HSC exam).
- **Groups**: from Class 9, each student is in a group (Science, Business Studies or Humanities), and subjects can differ by group.
- **Pass mark**: 33% of the full mark (`subjects.pass_marks` defaults to 33 on a 100-mark subject; Class 9-12 parts use the SSC/HSC split such as written 70/23). The old default of 40 graded D marks (33-39) as F; migration `2026_10_06_000001` changed the default and corrected legacy 100/40 rows in `subjects`, `class_subjects` and the `exam_subjects` of draft/marks-entry exams (processed/published snapshots are never touched).
- **Grading**: the Bangladesh GPA scale: A+ 80–100 = 5.00, A 70–79 = 4.00, A- 60–69 = 3.50, B 50–59 = 3.00, C 40–49 = 2.00, D 33–39 = 1.00, F 0–32 = 0.00.
- **Academic year**: January to December.
- **Money**: Bangladeshi Taka (BDT, ৳), stored and sent as `decimal:2` per the API guideline.
- **Time**: store and send timestamps in UTC (the app's `APP_TIMEZONE`, which stays `UTC`). Asia/Dhaka is the school's local time, used for display and for date-only defaults such as today's attendance date.
- **Language**: names and content may be in Bangla or English, so don't assume ASCII (post and page slugs are the deliberate exception).

## Repository layout

The whole application is a **single Laravel 11 app in `backend/`**. It serves three surfaces:

- `/`: public school website, server-rendered Blade and built for SEO (`routes/web.php`, `app/Http/Controllers/Web`, `resources/views/public`)
- `/admin/*`: admin SPA in Vue 3 + Pinia + Vue Router, mounted by `resources/views/admin.blade.php` and bundled by Vite from `resources/js/admin`
- `/api/*`: JSON API (`routes/api.php`, `app/Http/Controllers/Api`)

There used to be a separate `frontend/` Vue app, but it has been removed and the admin SPA now lives entirely in `backend/resources/js/admin`.

## Commands

Run all of these from `backend/`:

```bash
composer install && npm install
cp .env.example .env && php artisan key:generate   # .env.example defaults to sqlite
php artisan migrate:fresh --seed                    # roles/permissions, admin user, sample public content
php artisan storage:link                            # public disk (post uploads) served from /storage

composer dev          # serve + queue:listen + pail logs + vite, all at once
npm run dev           # Vite only (HMR on :5173, strictPort)
npm run build         # production assets

php artisan test                                   # full suite (sqlite :memory:, see phpunit.xml)
php artisan test --filter=PublicSeoTest            # one class
php artisan test --filter=test_public_page_is_server_rendered_with_seo_tags
./vendor/bin/pint                                  # code style (Laravel Pint)
```

Docker alternative (run from the repo root): `docker compose up` starts MySQL (host port 3307, db `scms`), the app on :8000 and Vite on :5173.

Seeded admin login: `admin@sms.com` / `password`.

## Architecture notes

- **Auth**: the admin SPA uses Sanctum **bearer tokens** stored in `localStorage` (`resources/js/admin/services/api.js`), not cookie/session auth. A 401 response clears the token and redirects to `/admin/login`. The Vue router uses `createWebHistory('/admin/')`, and the catch-all `Route::view('/admin/{any?}', 'admin')` in `web.php` serves every admin path.
- **Roles and permissions**: Spatie Permission. The `role` and `permission` middleware aliases are registered in `bootstrap/app.php`. Roles (admin/teacher/office/student/parent) and kebab-case permissions like `view-students` come from `RolePermissionSeeder`. Every authenticated API controller declares per-action permissions through `HasMiddleware` and `Controller::resourcePermissions()`, except posts and pages, which use `role:admin`. `tests/Feature/ApiAuthorizationTest.php` fails if a route lacks a check, so new routes need a mapping or an explicit entry in its allowlist. Sections reuse the `*-classes` permissions, exam schedules reuse `*-exams`, and academic years are readable by any user but need `edit-settings` to change. Permissions are role-wide: nothing limits teachers to their own students, and parents and students don't have `view-students` at all (they use `/api/my/children` and `/api/my/student`, see the Students note).
- **Shared public content**: news and events are a single `Post` model split by `type` (`Post::TYPE_NEWS` / `TYPE_EVENT`). `App\Services\PostService` holds the read queries. Both the Blade site (`Web\PostController`) and the unauthenticated mobile-app API (`Api\PublicContentController`, `/api/public/*`, output through `PostResource`) use it, so the two always return the same data. Put new public-content queries in the service, not in a controller. Contact form submissions work the same way: `ContactService` (its validation rules are `ContactService::RULES`) is shared by the web form and `/api/public/contact`.
- **Post model behavior**: slugs are generated automatically and kept unique. Setting `is_published` fills in `published_at`. The `published()` scope also requires `published_at <= now()`. Saving or deleting a post clears the cached `sitemap.xml` (cached for 1 hour in `SeoController`). Post bodies are sanitized HTML, written by the Tiptap editor in the admin SPA and stored as-is: `App\Services\PostService::create()`/`update()` sanitize with `App\Support\PostBody::sanitize()` (the `post_body` profile in `config/purifier.php`, via `mews/purifier`) and reject a body that is empty after sanitizing. `PostBody::plainText()` produces the excerpt and meta-description fallbacks. The public page renders the stored HTML directly (`{!! $post->body !!}` in `resources/views/public/posts/show.blade.php`); there is a single render path, so nothing re-sanitizes on read. Uploaded images go through `POST /api/posts/media` (admin only) to the `public` disk under `posts/{Y}/{m}/{uuid}.{ext}`, served from `/storage/...` (`php artisan storage:link`). A one-off data migration converted bodies written before this feature (Markdown, rendered with `Str::markdown` at read time) to sanitized HTML.
- **Pages module**: standalone public content pages (policies, facilities, etc.), a full module on the Controller → Service → Repository pattern (`App\Models\Page`, `PageRepositoryInterface`/`PageRepository`, `PageService`, `Api\PageController` at `/api/pages`, `role:admin` like posts). Slug generation, the `published()` scope, sitemap-cache clearing on save/delete, and `PostBody::sanitize()`/`isEmpty()` on the body all mirror `Post`, reusing the same `post_body` purifier profile and `POST /api/posts/media` upload endpoint from the admin editor. The public route is `GET /pages/{slug}` (`Web\PageController`, view `resources/views/public/pages/show.blade.php`), named `page.show` (singular) so it doesn't collide with the `pages.show` name Laravel generates for `apiResource('pages', ...)`. Admins manage pages, and separately News and Events (same `Post` model, different `type`), under the sidebar's collapsible **CMS** group (`resources/js/admin/views/Layout.vue`); `/news` and `/events` reuse `PostList.vue`/`PostForm.vue` with the type fixed by route `meta.type`, and the old `/posts` routes redirect to `/news`. About stays hardcoded Blade, not a Page record (Admissions is dynamic, see the Admissions note).
- **Menu module**: the public header nav is an admin-managed, nested tree (`App\Models\MenuItem`, `MenuItemRepositoryInterface`/`MenuItemRepository`, `MenuService`, `Api\MenuItemController` at `/api/menu-items` plus `PUT /api/menu-items/reorder`, `role:admin` like pages). Each item has a `location` (only `header` for now), a self `parent_id` (`cascadeOnDelete`, so deleting a parent deletes its children), a `type` of `page`/`route`/`url`/`heading`, and the matching target field; `route_name` is whitelisted to `MenuItem::ROUTES`. `MenuService` enforces a maximum depth of 3, no cycles, the parent staying in the same location, and the target required by `type`, all as `ValidationException`s. `MenuService::headerTree()` builds the nested, filtered tree (dropping unpublished/missing-page items and headings left with no visible children) and caches it forever under `menu.header`; `MenuItem` and `Page` save/delete hooks both forget that key, so publishing state changes take effect on the next request. `App\View\Composers\HeaderMenuComposer` shares it with `layouts/public.blade.php` as `$headerMenu`, rendered by the `<x-header-menu>` component (`resources/views/components/header-menu.blade.php`): CSS-only dropdowns on desktop (Tailwind named groups `group/lvl1`/`group/lvl2`, no JS) up to 3 levels, a `<details>` hamburger on mobile, and a hardcoded six-link fallback when the tree is empty. Admins manage it at `/admin/menu` (`views/menu/MenuList.vue`, `MenuForm.vue`), grouped under the sidebar's **CMS** section.
- **Media and Gallery modules**: photo/video galleries on the public site, two full modules on the Controller → Service → Repository pattern, `role:admin` like pages and menu. `App\Models\Media` (table `media`) is the reusable image library: one row per upload (`disk`/`path`/`original_name`/`mime_type`/`size`/`width`/`height`/nullable `alt`), managed at `/api/media` (`Api\MediaController`, index/store/update/destroy only — no `show`) and browsed/edited/deleted at `/admin/media` (`views/media/MediaLibrary.vue`). `App\Models\Gallery` (slug generation, `published()` scope and sitemap-cache clearing all mirror `Page`) holds ordered `App\Models\GalleryItem`s of `type` `image` (a `media_id`, restricted on delete so a library image in use can't be removed) or `video` (a `youtube_url` plus the `youtube_id` extracted from it); items are never a separate endpoint; the gallery's own store/update payload carries an `items` array that `GalleryService::syncItems()` (via `GalleryRepository`) creates/updates/deletes/reorders in one transaction, position in the array becoming `sort_order`. `items.*.media_id`/`items.*.youtube_url` are `prohibited_unless` the matching `items.*.type`, on top of the existing `required_if`, so an image item can't also carry a `youtube_url` or vice versa. `GalleryResource::withItems()` mirrors `PostResource::withBody()`: lists (`index`, `/api/public/galleries`, the `/gallery` and `/admin/galleries` grids) never carry every gallery's full `items` array, only `cover_url` and `item_count`, computed from a narrower eager load (`Gallery::firstImageItem()`/`firstVideoItem()`, one-of-many relations) instead of `items.media`; only `show`/`store`/`update` and `galleriesShow` opt in with `withItems()`. `App\Support\YouTube` is the one place that recognizes a YouTube URL (`watch?v=`, `youtu.be/`, `embed/`, `shorts/`, `m.youtube.com`) and extracts the 11-character id, used by both `Http\Requests\Gallery\Rules\ValidYoutubeUrl` (422 on anything else, including lookalike hosts) and `GalleryService`; the public page embeds `youtube-nocookie.com/embed/{id}` and uses `i.ytimg.com/vi/{id}/hqdefault.jpg` as the thumbnail. A gallery's cover is `cover_media_id` if set (`nullOnDelete`, so deleting that image falls back automatically), otherwise the first image item, otherwise the first video's thumbnail, otherwise null (the view/resource shows a placeholder). `Api\GalleryController` exposes the admin CRUD at `/api/galleries`; `Web\GalleryController` serves `GET /gallery` (`gallery.index`, paginated, 404 out of range) and `GET /gallery/{slug}` (`gallery.show`, a CSS-only `:target` lightbox for photos — see `.gallery-lightbox` in `resources/css/public.css` — and responsive video embeds), both through `GalleryService` so they and `Api\PublicContentController::galleries()`/`galleriesShow()` (`/api/public/galleries`) always agree; `gallery.index` is in `MenuItem::ROUTES`. Admins manage galleries at `/admin/galleries` (`views/galleries/GalleryList.vue`, `GalleryForm.vue`), adding items through the reusable `components/MediaPickerModal.vue` (a Library tab to search and multi-select existing images, an Upload tab that uploads new ones and selects them), under the sidebar's **CMS** group. `Database\Seeders\GallerySeeder` (called from `DatabaseSeeder`, matched by slug so re-running it never duplicates) draws placeholder JPEGs with GD straight to the `public` disk (no network) for a handful of Bangladeshi-school galleries.
- **Institute settings**: the school's identity, branding, contact details and address are admin-managed, not hardcoded. A generic `settings` table (`App\Models\Setting`: `key` unique, `value` text) backs it; `App\Support\InstituteSettings` is the registry of every key the "institute" group uses (grouped as identity/branding/contact/address/location/social, plus the education board and division option lists and the validation rules for each key). `App\Services\InstituteSettingsService::all()` returns every registry key (null when unset), cached forever under `settings.institute`; `update()` upserts only the keys that were sent, stores `logo`/`favicon` uploads as `settings/{uuid}.{ext}` on the `public` disk, deletes the old or removed file only after the write commits, and forgets the cache. `profile()` is the effective public read: it falls back field-by-field to `config('seo.*')` so an empty table renders exactly as it did before this module existed, and it's the only thing public readers use — never `all()` or `config('seo.*')` directly. `Api\InstituteSettingsController` exposes `GET`/`PUT /api/settings/institute` (`view-settings`/`edit-settings`, the same permissions `AcademicYearController` uses for its own settings actions); the admin SPA page is `views/settings/InstituteSettings.vue`, first in the sidebar's **CMS** group. `App\View\Composers\InstituteComposer` shares `profile()` as `$institute` with `layouts.public`, every `public.*` view, `components.seo` and `admin`, so the header logo/name, footer address, the contact page, `<title>`/favicon and `App\Support\SchemaOrg`'s JSON-LD (`alternateName` from `name_bn`, `geo` when both coordinates are set, and `addressCountry` hardcoded to `BD`) all read from the same values. `Api\PublicContentController::school()` (`/api/public/school`) reads the same `profile()` and keeps every pre-existing key alongside the new ones.
- **Admissions**: online applications for admission rounds, full modules on the Controller → Service → Repository pattern (`AdmissionRound`/`AdmissionRoundClass`, `AdmissionApplication`; `AdmissionRoundService`, `AdmissionApplicationService` for admin review, `AdmissionService` for the public side). A round belongs to an academic year, has `opens_at`/`closes_at` (Asia/Dhaka dates, close on or after open), `is_published`, sanitized `instructions_*` and per-class `seats` (nullable; `requires_group` is derived from class number >= 9); deleting a round with applications is a 409. Applications are numbered `ADM-{round's year}-{000001}` from a locked counter (select first, retried on deadlock, like fee receipts), with a unique `(round_id, birth_registration_number)` so a child applies once per round. Only the photo upload is required (jpg/png, 2 MB); the birth certificate and previous-school document are optional (jpg/png/pdf, 5 MB). Files go to the **private** `local` disk (`admissions/{uuid}.{ext}`), never a public URL; admins read them through `GET /api/admission-applications/{id}/files/{kind}` (`edit-students`, streamed `private, no-store`). Public site (`Web\AdmissionController`, all through `AdmissionService`, which `Api\PublicContentController::admissionRounds()`/`admissionStatus()` at `/api/public/admission-*` share): `/admissions` (indexable, open rounds), `/admissions/apply/{round}` (indexable while the round is open, 404 otherwise; CSRF, honeypot, generous `admission-apply` throttle plus 10 *saved* applications per IP per hour inside the service, hashing the IP with sha1; per-IP limits key on `$request->ip()`, so `TRUSTED_PROXIES` must be set behind a proxy), the noindex/no-store `/admissions/submitted` confirmation (one-shot: a refresh redirects to `/admissions`; uploaded PDFs are served as attachments, images inline, all with `nosniff`), and `/admissions/status` (POST, application number + date of birth, identical response for every miss, `admission-status` throttle and an hourly cap on misses; the form never flashes the date of birth: the web redirect drops it and the API returns 422 JSON, including without an `Accept` header); the status shows name, class, status, test time (Dhaka) and venue, never the admin note or private fields. Admin API (`*-students` permissions, office included): `/api/admission-rounds`, `/api/admission-applications` (+ `/counts`), `PATCH .../status` (transitions in `AdmissionApplication::TRANSITIONS`, `test_at` required for `test_scheduled`, approving checks the class's seats under a lock on the round row, 409), `POST .../convert` (approved only; calls `StudentService::create()` with the round's academic year, copies the photo, shares the guardian login by mobile, marks the application `admitted`). Birth registration number, mobiles, addresses and the admin note appear in admin responses only for `edit-students` (`AdmissionApplicationResource::withSensitive()`). SPA: `views/admissions/` (`AdmissionApplications.vue`, `ApplicationDetail.vue` which fetches documents as blobs with the bearer token, `AdmissionRounds.vue`, `AdmissionRoundForm.vue`) and an **Admissions** sidebar item under Students. Print options (see `docs/tasks/admission-print.md`): the family's printable copy is the partial `public/admissions/copy.blade.php` (school header from `InstituteSettingsService::profile()`, Bangla-first with English labels, A4 portrait print CSS that hides the site header/footer; birth registration masked to the last 4 digits via `AdmissionApplication::maskedBirthRegistration()`, never the admin note or score). It is rendered inline on the one-shot confirmation page and on the successful `POST /admissions/status` result, where it is hidden on screen and shown only by the print CSS (so there is no second request and no URL carrying the application number or date of birth); a status miss renders no copy. The photo sits on the private disk, so the copy's `<img>` uses `URL::temporarySignedRoute('admissions.copy-photo', 10 minutes)` (`GET /admissions/copy-photo/{application}`, `signed` middleware so a missing, tampered or expired link is 403, behind `PortalHeaders`, `AdmissionService::photoFile()`): it streams only the `photo` kind, `no-store`/noindex/`nosniff`, and only the copy pages generate that URL. Admins print one full form (`views/admissions/ApplicationPrint.vue`, `/admin/admissions/applications/:id/print`: Bangla/English toggle, photo as a blob through the authenticated download, document checklist, signature lines, sensitive fields only with `edit-students`) and the filtered list (`ApplicationListPrint.vue`, `/admin/admissions/print?round_id=&class_id=&status=&search=`: pages through `GET /api/admission-applications` at `per_page=100` up to 1000 rows with a notice if capped, landscape, repeated `thead`, guardian name and mobile only with `edit-students`). No server PDF and no batch form printing.
- **SEO**: every public page yields a `<x-seo>` component (`resources/views/components/seo.blade.php`) into the `seo` section of `layouts/public.blade.php`. The component handles the title, description, canonical URL (via `App\Support\Seo::canonical()`, which keeps only `?page=N` when N > 1), OG/Twitter tags and JSON-LD (built with `App\Support\SchemaOrg`). Site and organization values come from `App\Services\InstituteSettingsService::profile()` (the admin-managed institute settings), falling back field-by-field to `config/seo.php` (`SEO_*` / `SCHOOL_*` env vars) when a setting is unset. `tests/Feature/PublicSeoTest.php` requires each public page (including `/admissions`, the apply form and `/admissions/status`) to have the full SEO head and **exactly one `<h1>`**, and requires unknown or draft posts/pages to return a noindex 404. `Web\PostController` also returns 404 for out-of-range pagination pages. Keep new public pages consistent with these rules. Result pages follow the same rules: `/results` and `/results/archive` are indexable and in the sitemap (the sitemap lists only those two, never an exam or a student), while the marksheet that `POST /results` renders is `noindex, nofollow` with no canonical and `Cache-Control: no-store`.
- **Vite entries**: there are two, `resources/css/public.css` (the public site, Tailwind) and `resources/js/admin/main.js` (the admin). The `@` alias points to `resources/js/admin`.
- **Model naming quirks**: the class model is `App\Models\Classes` (table `classes`), because `Class` is a reserved word. The class–section pivot is `ClassSection`. A guardian is a `User` with the `parent` role (`User::children()` returns their students); there is no parent model.
- **Dashboard**: `GET /api/dashboard` (`Api\DashboardController`, `role:admin|office|teacher`, so students, parents and role-less users get 403; the old `dashboard/stats` and `dashboard/recent-activities` routes and the last stub controller are gone, so **no stub controllers remain**). `DashboardService::forUser()` picks one payload by role, the widest of admin > office > teacher, for the active academic year and "today" in Asia/Dhaka; with no active year it returns only `{role, today, academic_year: null}`. **Admin**: `counts` (students total / `by_level` / `by_group` / `by_shift`, active staff / teachers / `with_login`, active sections), `attendance_today`, `exams` (`latest` non-draft exam by start date, `classes` with `{class, students, passed, pass_rate, top_gpa}` once results exist, `marks_entry` with `incomplete_sheets`/`total_sheets`/per exam), `fees` (`month` = net / collected / outstanding of dues falling due this month, `today` = count, amount and `by_method` for all four methods, `overdue` = count and outstanding of dues past `due_date` and not fully paid) and `recent` (5 payments, 5 processed/published exams, 5 admitted students). **Office**: `collection_today`, `month`, `students_with_outstanding_dues` and the 10 latest `recent_payments`, no exam or attendance blocks. **Teacher** (through `TeacherScope::forUser()`): `attendance_today` of the sections they lead (each section summary, in every role's payload, carries `class_teacher: {id, name_en, name_bn}|null`, the **main** class teacher for the year, loaded by `DashboardRepository::sections()` in one extra query; `Dashboard.vue` shows the name after the section), `mark_sheets` for exams in `marks_entry` limited to their own (section, class, subject) assignments with `entered`/`total`, and `pass_rates` of the latest exam in the sections they lead; a teacher with no staff link or assignments gets empty lists, never a 500. `attendance_today` is `{date, is_school_day, holiday: {type: holiday|weekly, name_en, name_bn}|null, sections_marked, sections_not_marked, percentage, sections: [{section, students, marked, present, absent, late, leave, percentage}], not_marked}`: only active sections with active enrolments are listed, "present %" counts present + late as attended (like `SchoolDays::percentage()`), an unmarked section has `percentage: null`, and a holiday or weekly holiday (`HolidayRepository::findByDate()` / `InstituteSettingsService::weeklyHolidays()`) makes nothing "not marked". Money and percentages are `decimal:2` strings (`Money::fromPaisa()` of the summed database value, whatever type the driver returns). Every figure comes from an aggregate query in `DashboardRepository` (`count`/`sum`/`group by`, behind `DashboardRepositoryInterface`), so the query count depends on the role and not on the number of students or sections (`DashboardApiTest::test_the_query_count_does_not_grow_with_students_or_sections`). Student counts and "how many students should have marks for a sheet" both come from one query of active enrolments grouped by `(section, group, 4th subject)`; the sheet totals apply `StudentEnrolment::takes()` (the mark sheets' own rule) to those groups instead of querying per sheet. A month's "collected" is paid against that month's dues, so collected + outstanding = net. The admin `views/Dashboard.vue` renders the payload per role: stat cards, accessible one-hue `components/BarList.vue` bars with the value printed beside each bar (no chart library), empty states for a holiday, no exam yet and no fees, and quick actions filtered by `canAccess()` (a teacher sees Mark attendance and Enter marks only; office sees Collect fee).
- **Staff and Shifts modules**: current and former teaching/non-teaching staff, shown on the public স্কুল প্রশাসন (School Administration) pages, and the shifts they belong to. Both are full modules on the Controller → Service → Repository pattern, replacing the old placeholder `Teacher` model/table/`TeacherController` stub wholesale (`subject_assignments.teacher_id` is repointed to `staff_id`, and `SubjectAssignment::staff()` replaces `::teacher()`). `App\Models\Staff` (table `staff`, soft deletes) has a nullable `user_id` (logins are linked later), `category` (teacher/staff), `position` (head/assistant_head/teacher/staff), `status` (active/retired/transferred/resigned/deceased), and the usual personal/contact/address fields; `name_en`/`name_bn` each may be blank but not both (enforced in `StaffService`, not the database, so it's still checked on a partial update against the model with the input applied — the same pattern as `SubjectService::ensurePassMarksWithinTotal()`). `App\Models\StaffEducation`/`StaffTraining` (tables `staff_educations`/`staff_trainings`) are child rows managed entirely through the staff store/update payload's `educations[]`/`trainings[]` arrays, synced like `GalleryService::syncItems()` (`StaffRepository::syncEducations()`/`syncTrainings()`; each re-fetches `$staff->{$relation}()` fresh for every query rather than reusing one builder, because `HasMany` forwards `where()`/`whereKey()` onto the same underlying query instance, so reusing it would let one iteration's `whereKey()` narrow every later call including the final delete). `App\Models\Shift` (table `shifts`) holds `name_en`/`name_bn`, a unique ASCII `slug`, and nullable Asia/Dhaka wall-clock `start_time`/`end_time`; every staff member has at least one shift via the `shift_staff` pivot. `StaffService` enforces: a non-`active` status requires `leaving_date`; `leaving_date` must be on/after `joining_date`; and each shift can have at most one active `head` and one active `assistant_head` (`StaffRepository::hasActiveInPosition()`). Photo replace/remove follows `InstituteSettingsService::update()`'s file-handling pattern (delete the new file on failure, the old one after commit). `Api\StaffController` (`/api/staff`) reuses the `*-teachers` permissions from `RolePermissionSeeder`; `Api\ShiftController` (`/api/shifts`) reuses `view-settings`/`edit-settings` like `AcademicYearController` (reads open to any signed-in user, writes need `edit-settings`). `Web\StaffController` serves the 7 public index pages (`staff.head`/`assistant_head`/`teachers`/`employees`/`ex_heads`/`ex_teachers`/`ex_employees` at `/administration/...`) and `staff.show` (`/administration/staff/{staff}`), all through `StaffService::publicList()`/`publicFind()`, the same methods `Api\PublicContentController::staff()`/`staffShow()` (`/api/public/staff`) use, so the website and the mobile API always agree; neither ever exposes `nid`, `date_of_birth`, addresses or `mpo_index`, and `mobile`/`email` only appear when `show_contact` is set (`StaffResource::public()`, mirroring `GalleryResource::withItems()`). List pages take an optional `?shift={slug}` filter, resolved by `StaffService::resolveActiveShift()` (aborts 404 for an unknown or inactive slug, matching an unknown page/post slug); the filter pills only render when more than one active shift exists. A successful login marks that user and IP pair as trusted for 30 days (`login-trusted:{id}:{version}:{sha1(ip)}` in the cache, via `App\Support\LoginTrust`), and a trusted IP skips the per-account lock, so an attacker hammering a known account from elsewhere can't keep its owner out; the per-IP limit still applies to it, and `change-password` revokes the user's other tokens. The `{version}` is a per-user counter (`login-trust-version:{id}`, default 0): `LoginTrust::invalidate($user)` bumps it, which drops every trusted IP of that user at once, and is called wherever credentials change or a login is switched off (`AuthService::changePassword()`, and next to every `revokeAllTokens()` in `StudentService`/`StaffService`: an admin password reset of a student, guardian or staff login, and a deactivation), so a new code path that revokes tokens or resets a password must call it too. These limits (and the public result lookup's) key on `$request->ip()`. By default no proxy is trusted, so `X-Forwarded-For` is ignored and the socket IP is used; behind Cloudflare or a load balancer set the `TRUSTED_PROXIES` env var (comma-separated addresses/CIDRs, or `*`; documented, commented out, in `.env.example`). It is read by `config/app.php` (`app.trusted_proxies`, so it works with `config:cache`; reading `env()` in `bootstrap/app.php` runs before `.env` is loaded and never applied) and applied in `AppServiceProvider::boot()` through `App\Support\TrustedProxies::apply()` (`TrustProxies::at()` plus `withHeaders()`), only when it holds at least one non-empty entry (blank entries from a trailing or doubled comma are dropped; an empty or null value calls `TrustProxies::flushState()`, clearing any earlier trust); only the `X-Forwarded-For`/`-Proto`/`-Port` headers are trusted, never `-Host`. `*` is only safe when the app is reachable exclusively through a proxy that overwrites or appends `X-Forwarded-For`; otherwise anyone can spoof their IP and bypass the login and result-lookup limiters, so prefer listing the proxy's own IPs/CIDRs. Without it every visitor behind a proxy would share the proxy's IP (one 30-failure burst would block the whole site and one trusted IP would cover everyone). Accepted trade-offs: a user with no trusted IP yet (first login or a new device) can still be locked out for a minute at a time, and someone on a shared school network can block that network for a minute with 30 bad attempts. The bulk form `PUT /api/sections/{section}/subject-teachers` (`{academic_year_id, assignments: [{subject_id, staff_ids: []}]}`, on `Api\SectionController`, `edit-classes`, registered before the sections `apiResource`) replaces the section's assignments for that year in one transaction: each subject gets exactly its `staff_ids`, an empty list removes the subject's teachers, a subject left out is removed too, errors are keyed per row (`assignments.2.subject_id`, `assignments.2.staff_ids.1`) and nothing is written when any row fails; removing is always allowed, even for a subject that has left the curriculum. `SubjectAssignmentService::canEnterMarks(User, Section, Subject, AcademicYear)` is the rule for mark entry (`ExamMarkService`, see the Exams and marks note): true for the `admin` role, otherwise when the user's linked staff row (`staff.user_id`) holds any of that subject's assignments for that year (every assigned teacher can enter marks) and the staff member is still `active` (a retired, transferred, resigned or deceased teacher is refused); teacher logins (linking staff to users) don't exist yet, so until they do only admins pass. Guards: `StaffService::delete()` returns 409 while the staff member has assignments, the class/section/year/subject delete guards already check this table, and `CurriculumService::sync()` returns 422 when a subject with an active-year-or-later assignment would leave the class's curriculum for that assignment's group. Admins assign teachers at `/admin/sections/:id/subject-teachers` (`views/sections/SubjectTeachers.vue`, linked from `SectionList.vue`): a year selector (default the active year), one row per curriculum subject of the class (filtered by the section's group when it has one), a checkbox per active teacher of the section's shift in each row (several teachers per subject) and one Save with per-row errors.

A sheet lists the active enrolments of the exam's year in the section (not soft-deleted students) whose student takes the subject: a compulsory row common to the class (no group) is taken by everyone, a compulsory row of a group by that group's students, and an optional row only by the students who chose it as their 4th subject (`optional_subject_id`, and in that group when the row has one). Reading and saving both need `SubjectAssignmentService::canEnterMarks` (403 `Only the assigned subject teacher or an admin can enter marks.`; the student and parent roles have no `enter-results`). - **Exam results and GPA**: processing an exam's marks into results, publishing them, and reading them back, on the Controller → Service → Repository pattern. `App\Support\Gpa` is the stateless helper with every grading rule (like `Seo`, no database): `gradeFor()` (the CLAUDE.md scale on a percentage compared half-up on 2 decimals), `unit()` (grades one subject, or a pair of papers combined), `result()` (GPA, overall grade, pass, failed count, totals), `gradeForGpa()` and `positions()`; all arithmetic is on integer hundredths so rounding is exact, and every number is sent as a `decimal:2` string. A **unit** is one subject, or the papers sharing a `paper_group` among the subjects the student takes (a group with one row is a single subject); it fails (F, 0.00) when the student was absent from any paper or any part's marks, summed across the papers, are below that part's pass marks summed across the papers; otherwise the grade comes from combined obtained over combined full. The student's **compulsory units** are every `compulsory` row they take (common rows plus their group's); the **4th subject** is the optional row matching the enrolment's `optional_subject_id`. GPA = (compulsory points + max(0, 4th-subject point - 2)) / number of compulsory units, capped at 5.00 and rounded half-up; any compulsory F makes the GPA 0.00, the grade F and the student failed, while failing the 4th subject never does. The overall grade is A+ at 5.00, then A from 4.00, A- from 3.50, B from 3.00, C from 2.00, D from 1.00, else F. `total_obtained`/`total_full` include the 4th subject. Merit positions use standard competition ranking (1, 2, 2, 4) within the class and, separately, within the section: GPA, then the number of subjects passed (`passed_count`: compulsory units with a grade other than F, a combined pair counted once, matching `failed_count`; the 4th subject never counts as a fail and never counts in `passed_count`, it only adds its bonus; the report card mutes a failed 4th subject with a "not counted as a fail" note), then total (roll number only orders the display; a failed student's 0.00 GPA keeps them below every passed student). `App\Models\ExamResult` (`exam_results`, one row per `(exam_id, enrolment_id)`) stores the totals, `gpa` (`decimal:2`), `grade`, `is_pass`, `failed_count`, `class_position`, `section_position` and a `subjects` JSON with one entry per unit (`exam_subject_ids`, `subject_ids`, `name_en`/`name_bn` (a pair's names joined with ` + `), `is_optional`, `is_combined`, per-`papers` detail, combined `parts` (`obtained`/`full`/`pass`), `obtained`, `full`, `percentage`, `grade`, `point`, `is_absent`), so a published result keeps the grading it was given. `ResultService` (`ExamResultRepository`, a narrow contract; the "who takes which subject" rule lives once in `StudentEnrolment::scopeTakingSubject()`/`scopeActiveIn()` and is shared with the mark sheets) does `process()`: under the exam lock, from `marks_entry` or `processed` (409 for a draft or published exam), it recomputes every active enrolment of the exam's year in every class of the exam (not soft-deleted students), replaces the exam's results in one transaction and sets `processed`; a paper with no mark row, or a non-absent mark row missing one of the paper's parts, counts as absent (an F) and is reported as `missing_marks` in the per class-and-section summary (`students`, `passed`, `failed`, `missing_marks`) the process response carries next to the exam. `publish()` needs `processed` (409 otherwise) and sets `published_at`; `unpublish()` returns to `processed`. `reopen()` (`POST /api/exams/{exam}/reopen`, `edit-exams`) is the explicit way back to editing: only from `processed` (409 from `published` with "Unpublish the results before reopening mark entry.", and from `draft`/`marks_entry`), under the exam lock it deletes the exam's results (`ExamResultRepositoryInterface::deleteForExam()`, before the status change) and sets `marks_entry`; the SPA's ExamResults.vue shows a "Reopen mark entry" button with a confirm for a processed exam. Saving marks into a `processed` exam sets it back to `marks_entry` (see Exams and marks), so stale results can't be published; a published exam still rejects marks (409). Known limit: a change that isn't a mark (an enrolment moved or removed, a class dropped from an unmarked exam) doesn't reset a `processed` exam, so process again before publishing. Guards against orphaned results (the soft delete doesn't cascade): `ExamService::delete()` is a 409 for a `processed` or `published` exam or one with any `exam_results` (`ExamRepositoryInterface::hasResults()`), `ExamService::update()` is a 409 for any `class_ids` change on a `processed` or `published` exam (other fields stay editable, with the date range rules still applied; the message is "Unpublish the results and reopen mark entry before changing this exam's classes." when published and "Reopen mark entry before changing this exam's classes." when processed), and `StudentService::delete()` is a 409 for a student with results (`StudentRepositoryInterface::hasExamResults()`). The own-schedule read decides "does the student take this subject" in memory with `StudentEnrolment::takes()`, which shares `StudentEnrolment::subjectRequirements()` with `scopeTakingSubject()` (one rule, no per-subject query). `per_page` on the tabulation is `integer min:1 max:100`. `Api\ExamResultController` has `POST /api/exams/{exam}/process|publish|unpublish` (`publish-exams`, teachers don't have it) and `GET /api/exams/{exam}/results?class_id=&section_id=&with_subjects=` (`view-results`; paginated tabulation ordered by section position when a section is filtered, otherwise class then class position; `ExamResultResource` rows carry a narrow student, roll, group, class and section, and `subjects` only with `with_subjects=1`, like `PostResource::withBody()`) and `GET /api/exams/{exam}/results/{student}` (the full breakdown, 404 without a result); the student and parent roles have no `view-results`. Own records, through `MyRecordsController` and `ResultService` (published exams only, so an unpublished or unpublished-again exam disappears): `GET /api/my/results` (`role:student`, the student's results with the full breakdown, 404 when no student record is linked), `GET /api/my/children/{student}/results` (`role:parent`; `StudentService::findChildOf()` gives 403 for any student who isn't the guardian's own, existing or not) and `GET /api/my/exams` (student or parent: one entry per student with the exams of their class in the active year that are not drafts, each listing only the subjects the student takes, with subject, date and time and no marks scheme). Report cards are a print-friendly SPA page, no PDF library: `views/exams/ReportCards.vue` at `/admin/exams/:id/report-cards?class_id=&section_id=` (and `/report-cards/:studentId` for one student) loads the results with `with_subjects=1`, the exam and `/api/public/school`, and prints one card per page (`@media print`, `break-after: page`, the sidebar and top bar hidden through a `report-cards-page` class on `<body>` while the page is mounted) with Noto Sans Bengali from Google Fonts; `views/exams/ExamResults.vue` at `/admin/exams/:id/results` has the Process, Publish and Unpublish buttons, the processing summary and the tabulation, linked from `ExamList.vue`. `ExamSeeder`'s HY-2026 exam can be processed straight away. Known curriculum limit: the curriculum can't express "Biology or Higher Math, one compulsory and the other the 4th subject", because the 4th subject is fixed per group (an `optional` row), so choosing which Science subject is the compulsory one per student is not supported; weighted or combined results across exams and promotion from results are also out of scope. **Choice pairs in results**: `exam_subjects` snapshots `choice_group` (generate and regenerate copy it). Who takes what is still only `StudentEnrolment::subjectRequirements()`/`takes()`/`scopeTakingSubject()`: the compulsory member of a pair is taken by every student of the group, and the optional member by a student whose `optional_subject_id` is either member (a student with another or no 4th subject takes only the compulsory member). `StudentEnrolment::hasAsFourth()` decides compulsory or 4th per student for `ResultService::gradeEnrolment()`: the pair member the student chose as the 4th subject is graded as optional (only the bonus above 2.00 counts, a fail does not fail them) and the other member as compulsory, whichever row is optional in the curriculum; `Gpa` is unchanged. The breakdown's `is_optional` per unit is what report cards and the public marksheet show as the 4th subject. `EnrolmentService::placementErrors()` (shared with promotion) accepts either pair member, or any plain optional row, as the 4th subject. **Existing results are not recomputed**: after changing a student's 4th subject or a curriculum pair, regenerate the exam's class schedule (before marks exist) and reopen and reprocess the exam to apply it; exams generated before the migration have no `choice_group` in their snapshot.

Weekly holidays are the `weekly_holidays` institute setting (a JSON list of weekday names stored in `settings`, validated in `App\Support\InstituteSettings`, default `['friday']`, never empty; read through `InstituteSettingsService::weeklyHolidays()`; the admin Institute page has a checkbox per weekday). `App\Support\SchoolDays` is the stateless helper: a school day is any date that is neither a weekly holiday nor a listed holiday, and `percentage()` formats (present + late) over school days as a `decimal:2` string. `AttendanceService` resolves a date's academic year from its calendar year (the date must also fall inside that year's start and end dates, else 422 on `date`), and **who may read or save a section is any class teacher of it for that year, main or co-teacher (`TeacherScope::forUser()->leadingSectionIds()`, staff still active), or an admin, else 403**; a subject teacher who isn't a class teacher, the office role, students and guardians cannot. Saving (`PUT /api/attendance/sheet`, `mark-attendance`) takes the section lock via `StudentEnrolmentRepository::lockSection()`, upserts the whole sheet in one transaction like `ExamMarkService::save()` (per-row errors `entries.N.student_id`; students not sent are left unchanged; `marked_by` is the current user on every saved row) and refuses, as 422 on `date`: a date after today in Asia/Dhaka, a listed holiday, a weekly holiday, and for a non-admin a date older than `AttendanceService::TEACHER_EDIT_WINDOW_DAYS` (today and the six days before it); admins may edit any past date. `GET /api/attendance/sheet` (`view-attendance`) lists the section's active enrolments by roll with any saved status, `is_holiday` and the `holiday` (`type` `holiday`/`weekly`, `name_en`, `name_bn`); `date` defaults to today in Dhaka (`AttendanceService::today()`, the only place that reads the clock). `GET /api/attendance/report?section_id=&month=YYYY-MM` returns `{month, section_id, school_days, students: [{student, days: {date: status}, totals, percentage}]}`: `school_days` are the school days of the month up to today and inside the year, a row recorded on a day that later became a holiday is ignored, a student who left (enrolment no longer active) appears with only the days recorded and is measured over those, and an active student over all school days so far. `GET /api/attendance/students/{student}?month=` returns one student's month plus `year_to_date` (school days, totals, percentage). `/api/holidays` is a full CRUD (`view-attendance` to read, `edit-settings` to write; index filters by `academic_year_id`; `AcademicYearService::delete()` also blocks on holidays). `GET /api/my/attendance` (`role:student`) and `GET /api/my/children/{student}/attendance` (`role:parent`, `StudentService::findChildOf()` gives 403 for anyone else's child) return the same `StudentAttendanceResource` through `AttendanceService::ownMonth()`/`childMonth()`, and the student and parent roles no longer hold `view-attendance`. The class, section and student `hasAttendances` guards read the new table (the class guard through its sections, soft-deleted ones included). The admin pages are `views/attendance/MarkAttendance.vue` (section and date pickers, click-to-cycle status, mark all present, per-row remarks and errors, holiday banner), `AttendanceList.vue` (printable monthly grid) and `Holidays.vue` (under **Academic**); `composables/useAttendanceSections.js` limits a teacher's pickers to `/api/my/assignments` `class_teacher_of`, and the sidebar shows Attendance to admins and to teachers who lead at least one section. Attendance starts at the enrolment: `student_enrolments.enrolled_on` (nullable date, Asia/Dhaka calendar date; null means the start of the year) is set by `EnrolmentService::save()` to today in Dhaka on a new enrolment (promotion passes the target year's start date) and was backfilled from the Asia/Dhaka date of `created_at`, or the year start if later. `AttendanceService` counts a student's school days from `max(range start, enrolled_on)` in the report, the student month and the year to date, and leaves a student who joined after the month out of its report. The sheet of any date lists the enrolments that were on the roll that day (`AttendanceService::onRoll()` over `AttendanceRepository::candidateEnrolments()`, every enrolment of the section and year): `enrolled_on <= date`, and a left or graduated student only while the student's `leaving_date >= date`; promoted and retained enrolments stay on. The access check runs before the date check, so a user who may not use the section gets 403 even for a date outside any academic year (with no year for the date, a non-admin is checked against the active year). `Database\Seeders\HolidaySeeder` (six fixed-date 2026 holidays, matched by `date`) and `AttendanceSeeder` (the last 5 school days of every seeded Section A, matched by `(enrolment_id, date)`, deterministic statuses) are called from `DatabaseSeeder`.
- **Fees**: heads, per-class rates, per-student waivers, dues, payments and printable receipts, replacing the unused `fee_types`/`fee_structures`/`fee_payments` stubs wholesale (their models, controllers and the broken `fee-payments/student/...` and `fee-payments/receipt/...` routes are gone). Every service has its own repository and interface (`FeeHeadService`, `FeeRateService`, `FeeWaiverService`, `FeeDueService`, `FeePaymentService`, `FeeReportService`). **Money is integer paisa everywhere**: `App\Support\Money` (`toPaisa()` parses a decimal string digit by digit, `fromPaisa()` writes a `decimal:2` string, `percentOf()` rounds half up to the paisa, so 33.33% of ৳1,000.00 is ৳333.30); services never add or compare money as floats, the models cast amounts to `decimal:2`, and the API sends strings. `App\Models\FeeHead` (soft deletes; unique uppercase `code`, `kind` monthly/one_time/per_exam, `is_active`) is charged at `App\Models\FeeRate` amounts per (head, class, academic year, optional group): a group is only allowed from Class 9, a group's rate beats the class-wide one, and uniqueness with a null group is checked in `FeeRateService` (a unique index treats nulls as distinct), as for curriculum rows. A rate in use by dues can be edited (existing dues keep their amount) but not deleted (409), and its head/class/year can't change. `App\Models\StudentFeeWaiver` is a percent (0-100) or a fixed amount, exactly one of the two (checked against the model with the input applied, so a partial update that switches type must send the other as `null`), one per student, year and head; it applies only to dues generated afterwards (re-applying to existing dues is deliberately not offered, since a due may be part-paid). `FeeDueService::generate()` (`POST /api/fee-dues/generate`, `dry_run` for the preview) makes dues for the active enrolments of a year: a monthly head gets one due per `YYYY-MM` (the given month, or January up to the current Asia/Dhaka month; a student whose `enrolled_on` is later owes no earlier month), a one-time head one per enrolment (`one_time`), a per-exam head one per exam (`exam:{id}`, only when `exam_id` is sent, and then only per-exam heads are generated, for the classes the exam is held for); the amount is the applicable rate (none or zero means no due, counted as `no_rate`), the waiver is applied then (a fully waived due is `waived`), the due date is the rate's `due_day` (default the 10th; an exam due falls on the exam's start date), and it is idempotent (`insertOrIgnore` on the `(enrolment, head, period)` unique key; the response is `{created, skipped, no_rate}`). `FeePaymentService::collect()` runs in one transaction with the student row locked first (`FeePaymentRepository::lockStudent()`, then the dues, then the per-year `fee_receipt_counters` row `for update` (selected first and inserted only when missing, so two payments never deadlock on an `INSERT IGNORE` shared lock; existing databases must re-run `RolePermissionSeeder` to give the office role its fee permissions); cancelling locks the student, then the payment): the amount must be above zero and within the outstanding total of the student's open dues (or of the chosen `due_ids`, paid in that order), it is allocated oldest `due_date` first, each due moving to `partial`/`paid`, and the receipt number is `{Asia/Dhaka year}-{000001}` from that counter (a refused payment rolls the number back; a cancelled receipt's number is never reused). cash needs no transaction ID; bKash/Nagad/Rocket need one (trimmed, uppercased, unique per method, and a cancelled payment keeps its ID reserved); `paid_at` defaults to now (UTC) and only an admin may send one. `cancel()` (`POST /api/fee-payments/{id}/cancel`, `delete-fees`, so admin only, with a required `reason`) marks the payment cancelled (no hard delete), keeps its allocations as history and recomputes each due's `paid_amount`/status from the allocations of payments that aren't cancelled; cancelling twice is a 409. Permissions: `fee-heads` and `fee-rates` use `view`/`create`/`edit`/`delete-fees`, `fee-waivers` reads need `view-fees` and every write `create-fees`, `fee-dues` reads `view-fees` and generate `create-fees`, `fee-payments` reads `view-fees`, `store` `collect-fees` and `cancel` `delete-fees`, `fee-reports` `view-fees`. The `office` role holds `view-fees`, `create-fees` and `collect-fees` (so it reads, generates dues, adds waivers, creates heads/rates and collects, but can't edit or delete a head or rate or cancel a receipt); teachers hold no fee permission; **student and parent no longer hold `view-fees`** (a migration also removes it from existing databases) and read their own through `GET /api/my/fees` (`role:student`) and `GET /api/my/children/{student}/fees` (`role:parent`, 403 for anyone else's child through `StudentService::findChildOf`), both `FeeReportService::ownFees()`/`childFees()` returning every due, every payment and the outstanding total. `FeeReportService` also serves `GET /api/fee-reports/dues` (per student of a section for a month or the year), `/collection` (a Dhaka date range, at most a year, totals by method and collector, cancelled receipts listed but not counted) and `/students/{student}/ledger` (dues and payments of a year in date order with a running balance; a cancelled payment is listed but doesn't move it). The class, academic year and student delete guards now check `hasFeeRatesOrDues()` (class, year) and `hasFeeDuesOrPayments()` (student). Admins and office staff use the sidebar's **Fees** group (`views/fees`): Collect (`CollectFee.vue`, search a student, tick dues or leave all unticked, pick the method, then the receipt opens), Dues, Reports (`FeeReports.vue`: dues by section, collection, ledger), and for the admin Heads, Rates (a grid per year and class with a column per group) and Generate (`GenerateDues.vue` with a preview); waivers are on `StudentDetails.vue`. `FeeReceipt.vue` prints in Bangla or English (Bangla digits through `banglaNumber.js`) on A4 or A5 landscape (half an A4), with the school header, the allocations by head and month, and a CANCELLED watermark, using the report-card print pattern (`@page` written into a `<style>`, `body.fee-receipt-page` hides the admin chrome). `Database\Seeders\FeeSeeder` (after `ExamSeeder`) seeds the four heads, 2026 rates per class (tuition from ৳500 to ৳1,200, Science higher from Class 9), dues up to the current month and two demo payments (cash, and bKash `DEMO0001`) marked by their note, and is idempotent.
- **Portal**: the student and guardian portal at `/portal` on the public site (server-rendered Blade under `resources/views/portal/`, Bangla-first via `BanglaNumber`/`BanglaDate`/`Money::display()`, extending `layouts.public`; `portal/layout.blade.php` holds the single `<h1>`, the `noindex` `<x-seo>` head, the child switcher and the tabs). Auth is a **session (web guard)** login, separate from the admin SPA's bearer tokens: `Web\PortalAuthController` calls `AuthService::authenticate()` (the login lookup, per-account/per-IP failure locks, trust version and inactive-account rule that `AuthService::login()` also uses, minus the Sanctum token, so a browser sign-in never leaves a stray token) behind the same `throttle:login` limiter as `POST /api/login`, then `Auth::guard('web')->login()` plus `session()->regenerate()`. Only the `student` and `parent` roles get a session; a staff user who signs in with correct credentials is **redirected to `/admin/login?from=portal` without a session**, and a staff web session gets 403 on portal pages. Wrong password, unknown login and inactive account all show one generic bilingual message. The `portal` middleware group (`bootstrap/app.php`: `PortalHeaders` then `PortalAuth`) sends guests to `/portal/login`, signs out a deactivated user, 403s other roles, and puts `Cache-Control: no-store, private` and `X-Robots-Tag: noindex` on every response (the login routes use `PortalHeaders` alone); `robots.txt` also disallows `/portal` and the sitemap never lists it. Reads go through `App\Services\PortalService`, which adds no queries: it picks `ownResults`/`ownMonth`/`ownFees`/`ownSchedule` for a student and `childResults`/`childMonth`/`childFees` for a guardian, i.e. the exact `MyRecordsController` calls, so the portal and `/api/my/*` always agree (`PortalTest` compares both). A guardian's child comes from `?student={id}` (checked by `StudentService::findChildOf()`, 403 for another family's child), is remembered in the session (`portal.student_id`), and falls back to the first child; a student's `?student=` is ignored; the switcher only renders with 2+ children. `AttendanceService` additionally returns `non_school_days` (holidays and weekly holidays by date) for the month grid; `StudentAttendanceResource` does not expose it. Pages: `/portal` (dashboard), `/portal/profile` (+ `PUT /portal/profile/password` via `AuthService::changePassword()`, which revokes other tokens and bumps the trust version), `/portal/results` and `/portal/results/{exam}` (published exams only, reusing `public/results/marksheet.blade.php` with the same language/paper/orientation options), `/portal/attendance?month=YYYY-MM`, `/portal/fees` and `/portal/fees/receipts/{payment}` (`FeePaymentService::findForStudent()`, 404 for anyone else's payment), `/portal/exams` (exams not yet finished, subjects the student takes only). `portal.login` is in `MenuItem::ROUTES`, `MenuForm.vue` and `MenuSeeder` ("লগইন / পোর্টাল", appended once to an existing menu); when a student or guardian is signed in `<x-header-menu>` shows "আমার পোর্টাল" in its place plus a logout button. The receipt fixes are shared by the admin `FeeReceipt.vue` and the portal receipt: `App\Support\BanglaDate` (Bangla digits, month names, পূর্বাহ্ন/অপরাহ্ন, Asia/Dhaka) mirrored by `resources/js/admin/utils/banglaDate.js`, and cash is labelled "নগদ টাকা" (`FeePayment::METHOD_LABELS_BN`, `constants/fees.js`) so it isn't mistaken for Nagad ("নগদ (মোবাইল)"). Out of scope: online payment, messaging, editing the profile beyond the password.

## Development workflow

This repo ships a per-task agent harness under `.claude/`: slash commands, two subagents,
a smoke script and a `PreToolUse` gate hook. A task flows **spec → task file → branch →
code → test → smoke → commit → review → PR**.

**Who does what.** The main session (usually Opus) plans, asks the user questions,
delegates and reports. It does **not** write product code itself. Code comes from Sonnet:
the **`implementer`** subagent writes features, fixes and review follow-ups, and
**`test-runner`** fixes failing tests. Review comes from **`code-reviewer`** on Opus, so
the code is always reviewed by a different model from the one that wrote it.

- **`/new-task <spec>`** grooms the spec (problem, scope, acceptance criteria and
  **explicit test cases**), saves it to `docs/tasks/<slug>.md` (template in
  `docs/tasks/README.md`), and cuts `feat/<slug>` or `fix/<slug>` from `main`.
- **`/implement <task file | description>`** hands the task to `implementer` (Sonnet),
  checks the diff stays in scope, and reports. Follow-up fixes go back to `implementer`.
- **`/new-module <Model>`** plans a backend module and has `implementer` build it to the
  architecture guideline, using Subjects as the reference: repository interface and implementation, binding,
  service, FormRequests, resource, controller with permissions, routes and tests.
- **`/wrap-up [base]`** runs the end-of-task gate in this order:
  1. The **`test-runner`** subagent runs `php artisan test`, Pint on files added on this
     branch, and the hook classifier tests. It fixes failures until green.
  2. **Smoke:** `bash .claude/scripts/smoke.sh` seeds a throwaway SQLite database, boots
     the app on :8123, checks the public pages, `/admin`, the public API, an
     unauthenticated 401 and an admin login, then tears everything down. It never
     touches your real database.
  3. It updates the task file, then **asks** before committing.
  4. The **`code-reviewer`** subagent (read-only, runs on Opus, a different model from
     the Sonnet writer) reviews `base...HEAD` against `CLAUDE.md` and both guidelines, then
     records its verdict.
  5. If everything is green, it **asks** whether to push and open the PR.
- **`/pr-review [base]`** runs only the review step, for example after a fixup commit.
  It refuses on a dirty tree.
- Both review commands stop after **2 consecutive `changes-requested`** verdicts and hand
  the decision back to the user.

**Automated gates** (`.claude/hooks/gate.sh`, with commands classified by `classify.py`):
- `git commit` is denied on `main` or `master`. Use a task branch.
- `gh pr create` is denied unless `code-reviewer` recorded `pass` or `pass-with-nits` for
  the **exact current HEAD** on a clean tree. Receipts live in `.claude/.review-gate/`
  (gitignored, per machine).
- **`.claude/.review-gate/OVERRIDE`** disables both gates. Only the user creates it, by
  hand, outside Claude Code. Any tool call that tries to create or edit it is denied, and
  an agent must never suggest working around the gate by creating it.
- The hook is a cooperative guard, not a security boundary. Before changing
  `classify.py` or `gate.sh`, read their headers, then run
  `python3 .claude/hooks/test_classify.py`. Every case in it is a real bypass that was
  found and fixed.

## Architecture layers

Backend features follow Controller → Service → Repository interface → Eloquent repository. Controllers only handle HTTP, services hold the business rules and transactions, and repositories are the only place that builds queries. Every interface is bound in `RepositoryServiceProvider`. Subjects is the reference module. Legacy modules are converted only when they're otherwise being changed.
